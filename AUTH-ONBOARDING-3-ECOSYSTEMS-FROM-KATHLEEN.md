# Claude Code — Three Ecosystems, Three Friction-Free Journeys
### The auth & onboarding master spec for Relevé Connect
*Kathleen · July 25, 2026 · releve-platform · this governs every sign-up, sign-in, and onboarding decision*

---

## The governing principle (read first, applies to everything below)

Relevé Connect is now **three ecosystems — Professional, Studios, Families.** Each has
its **own first experience, and we only get it once.** That first moment cannot be redone.

**It must be friction-free.** If it is not smooth — if any single step feels like a hurdle —
people will not join. Not even if it's free, given away, or handed to them. Friction at
*any* step and they don't want in. The onboarding has to be smooth **from the very start**,
so each audience immediately sees the value and how Relevé helps them **Build, Grow,
Succeed, and Achieve.**

Every decision in this document is judged against one question: **does this add a step, or
remove one?** When in doubt, remove the step. Show the value before you ask for anything.

**Three audiences, three journeys — never one funnel.** Do not make one audience walk
another's path. A professional's first experience is not a family's. A studio's is not a
professional's. Build three clean journeys on the shared platform.

## Journey 1 — Professional · "Apply and be found"

**The value they must feel first:** *You will be discovered, hired, and credentialed.*

**Friction-free rule: the application is PUBLIC. No sign-in to apply.**
- **CRITICAL BUG TO FIX:** `/apply` currently redirects to `/login?next=/apply` — it forces
  a sign-in *before* the application appears. This is backwards and is the #1 friction wall.
  A professional applying for the first time **has no account yet.** Asking them to sign in
  before they can apply is the exact hurdle that makes them leave.
- **Fix:** `/apply` renders the application form immediately, to any visitor, with no
  auth step. Same open pattern the studio form already uses. They fill it out; they're in
  the pipeline. Authentication (the OTP) happens *later* — only when they return to manage
  their profile or once approved — never as the price of admission.

**The smooth path:** Homepage → "Apply to the Professional Roster" → application appears
instantly → submit → "You're in, we'll be in touch." That's it. The first experience is
*giving us their talent*, not *proving their email*.

## Journey 3 — Families · "Join through your studio"

**The value they must feel first:** *Your child's whole week — calendar, practice, daily
motivation, competition countdown, studio communication — in one calm place, plus the
door to what's next.*

This is the only journey that uses **two credentials**, so it is the one most at risk of
friction. Sequence it so it feels like **one smooth motion**, not two hurdles.

**The two credentials — kept distinct, never collapsed:**
1. **Studio join code (the membership card).** Generated by the studio *after it's approved
   and onboarded.* Answers *"do you belong here, and to which studio?"* Gates the family in
   and ties the account to that specific studio (studio-gated at the data layer). Without
   it, no family profile can be created.
2. **Email sign-in code / OTP (the front-door lock).** Answers *"is this really your
   email?"* The same 8-digit code every ecosystem uses. Temporary, changes every login.

**Friction-reducer — carry the studio code in the invite link.** Instead of making a parent
*type* a code, let the studio's invite be a link that pre-fills the studio
(e.g. a tokenized `/join` link). The parent clicks it → the studio is already recognized →
they only enter their email and the OTP. One typed thing, not two. (Still support manual
code entry as a fallback, but the link is the smooth default.)

**The smooth path:** Parent gets invite link from their studio → clicks → studio recognized →
enters email → types the 8-digit code → guardian account created, attached to the studio →
"This Week" appears. Membership card first, front-door lock second, value on screen third.

**Guardian model (keep clean for COPPA / Marshall Law):** The account is guardian-managed.
The **parent's** email receives the OTP; the **child never logs in directly.** The studio
code attaches the family to the studio; the guardian's email holds the login.

## The shared auth layer (one system, serving all three journeys)

**1. OTP for everyone — kill the magic-link loop. (Priority #1)**
- Switch from **magic links to a typed 8-digit one-time passcode.** Root cause of the
  current loop: emails go out as clickable magic links, and email security scanners
  (Microsoft/Outlook especially) *pre-click the link to inspect it*, which consumes the
  one-time token before the human ever sees it → "One-time token not found" / "otp_expired"
  → the endless "we sent a code" loop. A **typed code has no link to pre-click**, so it
  can't be burned out from under the user. This is the fix for the loop and needs no DNS.
- One code, generous expiry (~10–15 min), clear "enter this code" email — no link.

**2. Deliverability — the code has to actually arrive.**
- Today Supabase sends from its own shared address (`noreply@mail.app.supabase.io`), which
  **Microsoft/Hotmail silently drops** — so Hotmail/Outlook/iCloud users get nothing.
- Fix: send through **Resend** on the verified domain. DKIM and SPF are **already live and
  correct**; confirm the Resend dashboard shows the domain **Verified** (it may already be,
  on DKIM alone), then **switch Supabase's SMTP over to Resend and leave it on.** The one
  remaining DNS record (an MX on `send.send.releveconnect.com`) only affects bounce
  handling, not deliverability, and does **not** touch the root-domain email forwarding.

**3. Never gate the front door where it shouldn't be.** OTP is for *returning to an account*,
not for *first contact*. Professionals apply first (no auth). Studios request first (no
auth). Only families authenticate at join — and only after the value (their studio, their
week) is already in view.

## The friction kill-list (remove every one of these)

1. `/apply` login wall → **remove.** Application is public.
2. Magic links → **replace with typed OTP** (stops the scanner-consumed loop).
3. Codes not reaching Hotmail → **route through verified Resend**, leave it on.
4. Studio form "optional" fields + "Kathleen" copy → **fix** (see studio-form note).
5. Two typed codes for families → **collapse to one** via the invite link (studio pre-filled).

## Definition of done

1. **Professional:** Visiting `/apply` shows the application immediately — no sign-in step.
2. **Studio:** `/studios` form is public, all required fields enforced, copy corrected.
3. **Family:** Invite link pre-fills the studio; parent needs only email + one typed OTP;
   guardian-managed account lands on "This Week."
4. **Auth:** Every ecosystem signs in with a typed 8-digit OTP (no magic links); the studio
   join code remains a separate family-only gate; the guardian holds the login for minors.
5. **Delivery:** A test OTP arrives at Gmail **and** Hotmail **and** iCloud, and can be used
   once without looping.
6. **Smoothness:** Every journey shows value before it asks for anything. No step in any of
   the three journeys feels like a hurdle.
